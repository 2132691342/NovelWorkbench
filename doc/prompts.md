# 提示词资产

本文说明内置提示词的组织方式、每条的用途、编码与界面/工作流的契约，以及作者改动如何与出厂内容共存。
提示词的注入规则（系统级消息、占位符渲染）见 [ai.md](ai.md)；需要多步编排的任务见 [workflow.md](workflow.md)。

## 1. 设计取舍：少而清晰

内置提示词只保留 **3 个流程域 × (1 身份 + 1-3 任务) = 10 条**。这不是能力缩水，而是把复杂度放到了对的地方：

| 复杂度放哪 | 为什么 |
| --- | --- |
| 提示词只描述「这一单活怎么干」 | 作者在 `/` 菜单里要能一眼看懂每条干什么；几十条方法论只会让人不敢点 |
| 多步骤流程交给[工作流](workflow.md) | 步骤、门禁、重试由代码保证，不依赖作者记得按顺序点 |
| 长参考资料交给 `@` 引用与知识库 | 提示词正文里塞范文会让每次调用都变慢变贵 |

因此判断一条提示词该不该存在，标准是：**它是不是一个独立、常用、作者愿意主动触发的动作**。

## 2. 三层资产

| 层 | 落库位置 | 回答什么 | 什么时候用 | 注入角色 |
| --- | --- | --- | --- | --- |
| 身份提示词 | `prompts`（`prompt_kind_code=system`） | 我是谁、我的底线 | 整个会话常驻，可临时切换 | 系统级消息 |
| 任务提示词 | `prompts`（`prompt_kind_code=command`） | 这一单活怎么干 | `/编码` 单次触发，或工作流步骤引用 | 系统级消息 |
| 工具 | `tools` | 用确定性计算补事实 | 模型自行调用 | tool 消息 |

**注入约定（硬约束）**：提示词与上下文一律作为系统级消息进入消息序列，用户输入始终是用户级消息。
模型侧因此能区分「约束」与「要求」的边界。

## 3. 资产清单

### 3.1 写正文 `draft`（排序 10）

| 类型 | 编码 | 名称 | 用途 |
| --- | --- | --- | --- |
| 身份 | `novelist` | 连载作者（**默认身份**） | 只交稿、具体优先、节奏优先、章末留钩 |
| 任务 | `continue` | 续写正文 | 承接当前章往下写一段，不改前文 |
| 任务 | `chapter` | 写整章 | 按章节要求一次写完整章（工作流 `draft` 步骤默认用它） |

### 3.2 修问题 `revise`（排序 20）

| 类型 | 编码 | 名称 | 用途 |
| --- | --- | --- | --- |
| 身份 | `reviser` | 修订编辑 | 事实锁 / 声线锁 / 视角锁，只改怎么说 |
| 任务 | `polish` | 润色文字 | 去翻译腔、去重复、定性换现场（工作流 `revise` 步骤默认用它） |
| 任务 | `deai` | 去 AI 味 | 五类 AI 味命中清单 + 改写全文（`chapter_deai` 模板默认用它） |

### 3.3 做规划 `plan`（排序 30）

| 类型 | 编码 | 名称 | 用途 |
| --- | --- | --- | --- |
| 身份 | `planner` | 故事策划 | 结论先行、判断必带证据、材料不足即声明 |
| 任务 | `outline` | 搭大纲 | 卖点 / 世界观 / 主线 / 人物 / 分卷 / 章纲六层 |
| 任务 | `review` | 章节复审 | 输出严格 JSON 结论（工作流 `review` 步骤默认用它） |
| 任务 | `summary` | 章节摘要 | 四段式事实摘要（工作流 `summary` 步骤默认用它） |

默认身份提示词是 `novelist`（`sort_order=10`，`PromptRepo.GetDefaultSystem` 取启用的全局身份提示词中排序最前的一条）。

## 4. 编码契约

| 编码 | 被谁硬引用 | 改编码的后果 |
| --- | --- | --- |
| `continue` | 写作台编辑器「AI 续写」按钮 | 按钮点了没反应 |
| `polish` | 写作台「AI 润色」按钮、`chapter_polish` 模板 | 润色入口与打磨工作流失效 |
| `summary` | 写作台「AI 梗概」按钮、`chapter_draft` 模板 | 摘要步骤失败 |
| `deai` | 体检面板「让 AI 修」、`chapter_deai` 模板 | 去 AI 味入口失效 |
| `chapter` | `chapter_draft` 模板的起草步骤 | 逐章成稿无法出稿 |
| `review` | `chapter_draft` 模板的复审步骤 | 复审步骤失败 |

其余编码（`outline`）只在提示词库与 `/` 菜单出现，不构成硬编码依赖。

`/` 触发词由写作台本地动作与任务提示词共享。动作编码（`help`/`clear`/`new`/`attach`/`copy`/`check`/`focus`/`snapshot`）在 `domain.IsReservedActionCode` 里保留，
保存同编码任务提示词会被拒绝。动作在客户端就地执行、不消耗模型；任务提示词以系统级消息注入。弹层里按来源标注「本地 / 注入」，作者不必猜哪条会花额度。

## 5. 构造规则

内置资产不是自由散文，而是带验收判据的作业单：

| 要素 | 作用 |
| --- | --- |
| 身份边界 | 明确「这一单活不做什么」，防止越界改写 |
| 交付格式 | 规定输出结构（清单 / JSON / 正文） |
| 验收判据 | 可检查的通过条件，而非主观形容词 |
| 禁止项 | 常见劣化写法作为反向约束 |

长度约束：任务提示词 300-700 字，身份提示词 150-400 字。超长方法论拆成「任务 + `@` 引用素材」两层。

结构化输出（如 `review`）在提示词里直接给出 JSON 结构与判定规则，服务端 `parseReviewVerdict` 解析并容忍围栏与前后解释；
解析失败时降级为纯文本结论，不中断运行。

## 6. 版本与作者改动

- **指纹升级**：提示词带 `asset_hash_text`（sha256），启动播种时与代码资产比对；一致跳过，不一致且未自改则覆盖，`customized_flag=true` 一律不覆盖。
- **下线清理**：不在当前清单中的内置编码直接删除（身份与任务合并成一个编码集合）；用户自建提示词不受影响。
- **编码不可变**：内置提示词的 `prompt_code`、`scope_code`、`prompt_kind_code` 不允许修改，因为它们同时是 `/命令`、前端入口与工作流步骤的契约。
- **作用域**：全局与项目两级，同编码项目提示词覆盖全局；`PromptService.PromptTextOf` 是工作流取正文的唯一入口，与对话期 `resolveByCode` 共用同一套优先级。

## 7. 与工具的分工

| 场景 | 用提示词 | 用工具 |
| --- | --- | --- |
| 要产出新文本 | ✅ | — |
| 要核对门禁、统计、检索既有数据 | — | ✅ |
| 结果必须可复现 | — | ✅ |

工具不由命令注入：对话开始前服务端把启用工具的声明随请求下发，模型自行决定调不调。工作流里的体检步骤直接调用 `ai/check.Analyze`，
与 `chapter_check` 工具共用同一份实现，因此两处判定永远一致。

工具清单与调用细节见 [ai.md](ai.md) 的工具一节。
