# 提示词资产

本文说明内置提示词的组织方式、每条的用途、编码与界面/工作流的契约，以及作者改动如何与出厂内容共存。
提示词的注入规则（系统级消息、占位符渲染）见 [ai.md](ai.md)；需要多步编排的任务见 [workflow.md](workflow.md)。

## 1. 为什么是 8 条，而且每条都很短

内置提示词 = **4 个创作流程 × 2 条任务 = 8 条**，全部是 `command` 类，没有内置身份提示词。
每条 300–900 字，只回答一件事：**这一单活具体怎么干、交什么样的东西**。

分工原则是「通用规则写一次，任务差异才做成选项」：

| 内容 | 放在哪 | 为什么 |
| --- | --- | --- |
| 文风禁则、AI 味清单、结构判据、事实锁定 | **内置作者人格** `ai.BaseSystemPrompt`（会话与工作流始终注入） | 这是「所有活都该守的底线」，写一次处处生效，作者不用挑 |
| 这一单活的输入、步骤、交付格式 | 每条任务提示词 | 任务差异才是作者需要选的东西 |
| 多步骤编排、门禁、重试 | [工作流](workflow.md) | 步骤与门禁由代码保证，不依赖作者记得按顺序点 |
| 长参考资料、范文、素材 | `@` 引用与知识库 | 塞进提示词会让每次调用变慢变贵 |

判断一条提示词该不该存在的标准是：**它是不是一个独立、常用、作者愿意主动触发的动作**。
判断一段话该放人格还是放提示词的标准是：**换一条任务，它还成立吗？** 成立就放人格。

这样做的收益是作者面对的是八份短说明，每份读完就知道「这条什么时候点」；
代价是单看一条提示词会显得单薄——通用规则在人格里，作者在会话中始终能看到。

人格里的规则清单（`backend/internal/ai/prompt_base.go`）：

- 交付标准：只交可用文本、不解释、不自评；材料不足时明说缺什么。
- 文风禁则：不写定性、不写对称排比、不用万能词、不用解释腔、不写空转段落、不替读者下结论。
- 对白与信息：每句争夺信息/权力/关系；删三句对白若剧情不受影响则无效。
- 结构与节奏：开场两百字进场景、单章至少两次转折且付代价、章末停在未闭合处、一章不引入三个以上新名词。
- 事实与一致性：改稿不动事实、人物只知他该知道的、专有名词照抄。

`TestBuiltinAssetChain` 断言人格长度在 600–1400 字之间，并逐条检查上述关键规则确实写在里面——
人格一旦被删空，任务提示词精简后就没人守这些底线了。

## 2. 4 流程 × 2 条清单

流程排序即创作作业顺序：先立骨架，再写正文，出问题再修，最后质检。

### 2.1 开书规划 `plan`（排序 10）

| 编码 | 名称 | 什么时候用 | 被谁引用 |
| --- | --- | --- | --- |
| `outline` | 搭大纲 | 只有题材和想法，需要卖点 / 世界观 / 主线 / 人物 / 分卷 / 章纲六层骨架 | 提示词库、`/` 菜单 |
| `chapter_plan` | 拆章纲 | 已有卷纲，要把一卷摊成逐章任务单（目标 / 阻碍 / 钩子 / 字数预算） | 提示词库、`/` 菜单 |

### 2.2 写正文 `draft`（排序 20）

| 编码 | 名称 | 什么时候用 | 被谁引用 |
| --- | --- | --- | --- |
| `chapter` | 写整章 | 章节任务单已就绪，要一次出完整一章 | 工作流 `chapter_draft` 起草步骤、提示词库、`/` 菜单 |
| `continue` | 续写正文 | 正文写到一半卡住，要从断点往下接一段 | 写作台「AI 续写」按钮、提示词库、`/` 菜单 |

### 2.3 修问题 `revise`（排序 30）

| 编码 | 名称 | 什么时候用 | 被谁引用 |
| --- | --- | --- | --- |
| `polish` | 润色文字 | 意思没问题，但句子绕、重复、定性太多 | 写作台「AI 润色」按钮、`chapter_polish` 打磨模板、提示词库、`/` 菜单 |
| `deai` | 去 AI 味 | 读起来像机器写的：模板腔、对称句、情绪直述 | 体检面板「让 AI 修」、`chapter_deai` 模板、提示词库、`/` 菜单 |

### 2.4 质检 `check`（排序 40）

| 编码 | 名称 | 什么时候用 | 被谁引用 |
| --- | --- | --- | --- |
| `review` | 章节复审 | 一章写完，要一个能发 / 要改 / 不能发的结论与问题清单 | 工作流 `chapter_draft` 复审步骤、提示词库、`/` 菜单 |
| `summary` | 章节摘要 | 要把一章压成事实底稿，供后续章节做连续性核对 | 写作台「AI 梗概」按钮、工作流摘要步骤、提示词库、`/` 菜单 |

### 2.5 身份提示词为可选自建

内置身份提示词由 `ai.BaseSystemPrompt` 承担，库里不播种身份类条目。
没有配置身份提示词的对话统一走 `ai.BaseSystemPrompt`，
`PromptService.SystemPromptOf` 在库内无可用身份时返回它，绝不返回空串。作者要固定风格，就在提示词库自建一条 `system` 类提示词。

自建身份提示词会**替换**内置人格而不是追加，因此想保留底线规则时，应在自建内容里包含同样的禁则，
或者只写风格偏好并把禁则交给任务提示词与人格共存的那一版。

## 3. 编码契约

编码是硬契约，改名会让前端入口与工作流步骤失效。

| 编码 | 被谁硬引用 | 改编码的后果 |
| --- | --- | --- |
| `continue` | 写作台编辑器「AI 续写」按钮 | 按钮点了没反应 |
| `polish` | 写作台「AI 润色」按钮、`chapter_polish` 模板 | 润色入口与打磨工作流失效 |
| `summary` | 写作台「AI 梗概」按钮、`chapter_draft` 模板摘要步骤 | 摘要步骤失败 |
| `deai` | 体检面板「让 AI 修」、`chapter_deai` 模板 | 去 AI 味入口失效 |
| `chapter` | `chapter_draft` 模板的起草步骤 | 逐章成稿无法出稿 |
| `review` | `chapter_draft` 模板的复审步骤 | 复审步骤失败 |

`outline` 与 `chapter_plan` 只在提示词库与 `/` 菜单出现，不构成硬编码依赖，但同样是内置清单的一部分（播种、下线清理、分组展示都按编码认）。

`/` 触发词由写作台本地动作与任务提示词共享。动作编码（`help`/`clear`/`new`/`attach`/`copy`/`check`/`focus`/`snapshot`）在 `domain.IsReservedActionCode` 里保留，
保存同编码任务提示词会被拒绝。动作在客户端就地执行、不消耗模型；任务提示词以系统级消息注入。

## 4. 构造规则

每条任务提示词只用四类段落，顺序固定（测试按段落标题断言）：

| 段落 | 作用 |
| --- | --- |
| 开场一句边界 | 这一单活是什么、明确不做什么 |
| `【输入】` | 三个占位符各是什么，冲突时以谁为准 |
| 做法 / 要满足 | 分步骤执行顺序或交付要点，可核对 |
| `【输出格式】` | 交付结构（表格 / JSON / 纯正文），写作类明确「只输出正文」 |
| `【不做】` | 这条活不该做的事（写作类同时兜住「只交正文」） |

长度约束：每份 300–900 字（中文），单文件 ≤500 行。方法论与禁则交给人格，任务提示词不重复。

### 4.1 写作类：只交正文

`chapter` / `continue` / `polish` / `deai` 的输出会被**原样写进章节正文**，因此这四条一律硬约束「只输出正文，
不写标题、不列命中清单、不写改动说明、不加序号」。`TestWorkflowBodyOnlyPromptChain`（`backend/internal/service/workflow_chain_test.go`）
遍历这四个编码，断言正文里不出现「先列」「再输出改写」「输出格式：」「1. 先」这类要求先输出过程的正面指令；
`TestPromptAssetChain` 用同一份编码集合再守一遍，两处断言都不放宽。

### 4.2 复审：严格 JSON

`review` 的正文直接给出结构与判定规则，服务端 `parseReviewVerdict` 解析并容忍围栏与前后解释；
解析失败时降级为纯文本结论，不中断运行。

```json
{"verdict_code":"pass|revise|block","score_value":0-100,
 "issue_list":[{"level_code":"P0|P1|P2","issue_text":"...","quote_text":"...","fix_text":"..."}]}
```

判定规则：有 P0 必为 `block`；无 P0 有 P1 必为 `revise`；只有 P2 或清单为空为 `pass`。
每条 `issue_text` 必须能定位到 `quote_text` 原句，`fix_text` 必须能直接替换。

### 4.3 摘要：只记事实

`summary` 输出四段固定小节（发生 / 变化 / 遗留 / 位置），不评价、不推测、不加对白。
这份文本会进 `chapter_summaries` 并作为后续章节的上下文注入，写进评价就等于把评论当事实喂给下一章。

## 5. 版本与指纹

- **指纹升级**：提示词带 `asset_hash_text`（sha256，覆盖编码/名称/种类/分类/说明/排序号/正文），启动播种时与代码资产比对；
  一致跳过，不一致且未自改则覆盖，`customized_flag=true` 一律不覆盖。
- **下线清理**：`dropRetiredBuiltins` 删除 `builtin_flag=true` 且不在当前内置清单中的行，**不看种类**——
  已下线的身份提示词（`novelist` / `reviser` / `planner`）因此会在升级后被清掉；用户自建提示词不受影响。
- **编码不可变**：内置提示词的 `prompt_code`、`scope_code`、`prompt_kind_code` 不允许修改，因为它们同时是 `/命令`、前端入口与工作流步骤的契约。
- **作用域**：全局与项目两级，同编码项目提示词覆盖全局；`PromptService.PromptTextOf` 是工作流取正文的唯一入口，与对话期 `resolveByCode` 共用同一套优先级。

## 6. 与工具、工作流的分工

| 场景 | 用提示词 | 用工具 | 用工作流 |
| --- | --- | --- | --- |
| 要产出新文本 | ✅ | — | — |
| 要核对门禁、统计、检索既有数据 | — | ✅ | — |
| 结果必须可复现 | — | ✅ | — |
| 多步骤 + 人工审核点 | — | — | ✅ |

工具不由命令注入：对话开始前服务端把启用工具的声明随请求下发，模型自行决定调不调。工作流里的体检步骤直接调用 `ai/check.Analyze`，
与 `chapter_check` 工具共用同一份实现，因此两处判定永远一致。

工具清单与调用细节见 [ai.md](ai.md) 的工具一节。
